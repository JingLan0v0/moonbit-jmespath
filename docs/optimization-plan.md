## 每次触发后的工作方式

1. 读取 AGENTS.md、本文件、progress.md 和 acceptance.md，检查工作区、分支和最近提交；必要时核对远端。不要覆盖其他会话或用户新修改。
2. 选择最早未完成阶段中一个可独立验收的工作项。优先处理真实崩溃、错误结果、资源限制失效、失败 CI；出现紧急缺陷时插队处理，记录原计划续接位置。
3. 先定义成功标准和可复现输入，再实施。普通实现选择自行判断，不反复询问已授权步骤。账号失效、规则冲突或真正缺少信息时才向用户说明。
4. 完成该工作项的实现、相关测试和规定检查。不要仅提交计划、开始运行后结束，或用历史测试结果冒充本轮证据。
5. 有实际变更时更新 README/CHANGELOG/验收记录等受影响文档，使用普通提交同步原仓库，保留回溯；适用时核对该 SHA 的 Windows/Ubuntu CI。
6. 是否发布 Mooncakes 按变更性质决定。运行时代码或公共 API 改动执行完整发布流程；纯文档和测试工具改动通常不改库版本。不能覆盖已发布版本。
7. 结束前更新本文件“当前续接位置”和轮次记录，报告本轮完成内容、实际验证、剩余外部问题及下一项。

若时间或外部故障导致工作中断，记录具体文件、未通过命令、进程状态和下一步，不能写成完成。下次先完成该事项。一个阶段太大时拆成有独立验收结果的工作项，不强求一次跨完多个阶段。

这是一份由用户消息触发的工作流程，不意味着每隔几天自动运行。全部阶段完成后进入维护模式，根据真实使用反馈、覆盖缺口和性能数据选择下一项；没有证据时可以报告未发现新问题，不制造 bug、空提交或发布次数。

### P1：专项测试长期化

工作项顺序：

1. 整理 `_build/equality-audit-20261110.cjs` 为仓库内独立测试脚本。校验布尔/数字区分、键顺序、嵌套结构、Unicode、相等对称性、!= 与数组 contains 的一致性。保留独立预期算法。
2. 整理组合表达式生成测试，覆盖括号、投影、取反、引用和函数。固定种子、限制测试规模，避免每轮无限增加耗时。参考实现的差异必须逐项对照规范，不能把 Python 输出当成绝对真值。
3. 给失败案例增加最小化和重放能力。缩减时必须保留同一种失败，设次数/时间上限；将最终最小案例变成普通固定回归测试。

完成标准：干净克隆能够运行，无需本机 `_build`；debug/release 有实际计数与失败退出码；失败输入可重放；新运行先清除过期成功报告。外部参考依赖版本固定，测试数据/源码再分发遵循许可证，避免把临时第三方目录塞进包。大规模压力检查与日常检查可分档，但报告必须标明实际执行档位。

### P2：一条命令验收

建立跨平台总入口，串联静态检查、两种模式单元/CLI/API/边界测试、官方用例；Windows 包括 PowerShell 检查。复用现有脚本，避免每一层都重复构建和跑同一测试。CI 使用相同入口。

报告至少记录源码 SHA、是否有未提交修改、工具链/Node、构建模式、测试类别、实际计数、开始/结束时间、状态。区分 passed、failed 和未运行/网络阻塞，不将缺少测试伪装成通过。部分失败时也保留本轮可诊断的报告，不能留下旧 passed 文件。

完成标准：正常路径成功；可控失败（错误 CLI 路径、用例断言失败、不可用参考数据）会产生正确退出码和报告；测试网络故障使用隔离模拟，不改系统网络配置。完整验收与包预检、发布、安装、赛事结果分别记录。

### P3：公开 API 和数据修改行为

检查 Compiled 复用、修改调用方输入、修改返回数组/对象、字面量内部可变 Json、查询失败后再次调用等场景。重点验证是否会污染后续调用或绕过原来的数据检查。

这些是待验证风险，不是已确认缺陷。先确定 API 合理约定和最小复现，再选择隔离数据、适当复制或明确文档约定。若实施复制，必须评估资源计费与性能，不能无条件深复制所有输入。保留现有公共接口兼容性；需要改变语义时记录迁移影响和版本策略。

完成标准：输入/结果所有权约定清楚；编译对象重复使用及失败恢复有测试；已确认缺陷全部修复或诚实列为未解决，不能凭新增说明掩盖与既有承诺冲突的错误。

### P4：测量后优化性能

先建立固定数据与表达式的基准，分别测解析、预编译执行、完整 CLI、批量处理、排序、长字符串及序列化。覆盖小输入和接近合理边界的大输入，报告环境、输入规模、重复次数、耗时分布及可获得的内存指标，区分启动开销。

候选优化包括批次内重复表达式编译复用、重复形状遍历、排序中间分配等。只有测量确认瓶颈且语义和边界测试通过才实施。批次缓存如被采纳，须限制条目/总规模，明确与 Limits 的关系，每项独立 EvalState，不积累跨请求资源状态。

完成标准：可重复的修改前后对比，收益和代价可核查；正确性无回退，历史异常输入仍安全拒绝。不降低限制来冒充性能提升，不给共享 CI 主机设脆弱的绝对毫秒门槛。未发现有价值瓶颈时，可交付基准与结论，不强行修改算法。

### P5：错误诊断

审查目前常见 offset=0 的执行错误，优先改善函数参数类型、参数个数、未知函数和资源超限的定位。必要时为相关 AST 节点保留源码位置，先覆盖少数完整错误链路再扩展。

完成标准：错误代码保持兼容，位置单位仍清楚且一致（Unicode 标量与 UTF-16 不混淆），能定位含中文/emoji 的表达式；错误消息继续限长并安全转义；批次邻居不受影响；提升位置精度不削弱解析深度保护。不承诺所有错误都存在精确单点位置。

### P6：文档与演示

重新组织中英文 README，先展示用途、安装、最小示例、三个真实场景、限制、验证和发布状态。版本修复流水集中在 CHANGELOG 和 acceptance，避免首页成为过长的历史日志。

提供可执行演示：正常查询、带复杂投影的查询，以及同批次“正常—超限失败—正常”，输出有断言。明确批次外层 JSON 解析失败与单项查询失败的不同边界。以干净克隆实际运行文档命令。

完成标准：中英文版本、安装地址、API 示例、统计与真实状态一致；新用户无需翻聊天才能使用；评审能快速重现项目价值。若涉及新一轮参赛材料，重新核验当期官方规则，不沿用历史金额和截止时间。

### P7：最终交付复核与维护

核对源码、正常提交历史、对应 CI、许可证、引用声明、发布包排除项和当前版本。运行时版本变化时独立解压验证、正式发布并从注册表全新安装，在两种模式调用公共 API。

完成标准：每项证据对应准确提交/版本，不把旧发布回执视作当前结果；当前计划、progress、acceptance 和交接入口一致。用户身份操作、最终提交、评审和付款状态分别列明。
